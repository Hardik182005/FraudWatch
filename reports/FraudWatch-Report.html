2. Abstract, problem statement, objectives, CA1/CA2 mapping

Abstract

FraudWatch is a working fraud-detection system, not a mockup. Transactions from the IEEE-CIS Fraud Detection dataset are replayed onto Apache Kafka, enriched with per-account streaming features by Apache Flink and Apache Spark Structured Streaming, scored by a LightGBM model behind one shared HTTP scoring service, persisted to PostgreSQL, and streamed to two React websites. The whole backend runs on a single Google Compute Engine VM that wakes when a visitor arrives and stops itself after 45 idle minutes, so the deployment stays inside Google Cloud Free Trial credit. The system has been exercised end to end on GCP: 500 records processed by both engines with bit-identical scores, a measured late event path, a real TaskManager kill with checkpoint recovery, and a full sleep/wake/sleep lifecycle.

Problem statement

Card fraud must be caught while a transaction is still in flight, which makes it a streaming problem rather than a batch problem. Two properties make it hard. First, fraud is rare: in the held-out test split used here only 3.48% of transactions are fraudulent, so accuracy is a meaningless headline and precision/recall trade-offs dominate. Second, the arrival order is not guaranteed: events can arrive late or out of order, and a system that silently drops them reports a cleaner result than it earned. FraudWatch is built to make both of these visible rather than to hide them.

Objectives

  1. Replay a real, public fraud dataset through a real Apache streaming stack — no simulated brokers.
  2. Score every event with a trained gradient-boosting model and explain each decision with TreeSHAP.
  3. Report evaluation honestly: thresholds chosen on validation, held-out test reported separately.
  4. Compare Flink's record-at-a-time model against Spark's micro-batch model on identical input.
  5. Demonstrate event-time correctness (watermarks, late side output) and fault recovery (checkpoints).
  6. Deploy both websites publicly at zero out-of-pocket cost, with no dependency on a student's laptop.

4. Dataset, preprocessing, model design, evaluation, limitations

Provenance

IEEE-CIS Fraud Detection (Kaggle competition ieee-fraud-detection), contributed by Vesta Corporation. It is used under the competition's terms; the raw CSV files are not committed to the repository and are not shipped in the frontend bundle or any downloadable archive.

Units. TransactionAmt is reported by the source as a transaction amount in an unspecified currency unit. This report therefore calls it "transaction amount" and never relabels it as INR or any other currency. An earlier internal field name amount_inr was retired for exactly this reason.

Preprocessing and feature design

Only features computable from a stream were used — 15 in total (fs-1.1). A feature that needs the full dataset, or the future, cannot be computed when the transaction is actually in flight, so including one would inflate the score and break at runtime. Features combine per-event attributes with per-account state held in Flink's keyed ValueState (and Spark's GroupState), such as recent transaction counts and deviation from the account's own recent behaviour.

Model design

  • Main model: LightGBM gradient-boosted trees, artifact fw-ieee-stream-1.1.0.
  • Baseline: logistic regression, trained and evaluated on the identical split.
  • Explanation: per-event TreeSHAP (pred_contrib=True), contributions in log-odds, not probabilities.
  • Decision layer: rules-1.1 (deterministic rules) and policy-1.0 (alert / review / allow bands).

Evaluation — held-out test split (n = 88,581)

Thresholds were selected on the validation split and then applied unchanged to the held-out test split, which was scored once. Alert threshold 0.10477, review threshold 0.06955.

Reading these numbers honestly

Accuracy of 0.9059 looks strong and means almost nothing: always predicting "not fraud" would score about 0.965. The metrics that matter are PR-AUC 0.1375 against a 3.48% base rate, and a precision of 0.1508 at recall 0.3675 — roughly one in seven alerts is genuine fraud, and about two-thirds of fraud at that threshold is missed by the alert band alone. The model beats the logistic-regression baseline on PR-AUC by a clear margin (0.1375 vs 0.0961), which is the honest claim: it is better than the baseline, not that it is production-grade.

R3_TEST_THEN_LARGE fired zero times. That is reported as zero, not omitted. It means either the pattern is absent from this split or the rule's thresholds are too tight for it; which one has not been determined.

The model outputs are model scores, not calibrated probabilities, except where calibration is explicitly shown (Brier 0.0321, ECE 0.0055 are reported for the test split only).

Limitations

  • Trained on one public dataset from one contributor; no claim of generalisation to other issuers.
  • The 15-feature stream-computable subset is deliberately smaller than what a batch model could use.
  • No temporal drift analysis, no cost-sensitive threshold optimisation against real investigation cost.
  • The dataset's own labels are taken as ground truth; label noise is not modelled.

6. CA2 — Flink implementation and Spark comparison

Flink: event time, state, checkpoints

  • Event time, not processing time. Watermarks use forBoundedOutOfOrderness(5 s): the pipeline tolerates 5 seconds of out-of-order arrival before it considers a window closeable.
  • Windows. 60-second tumbling windows with allowedLateness(ZERO).
  • Late events are routed, not dropped. Anything arriving after the watermark has passed its window goes to a late side output and is persisted with a late flag. This is the design decision that makes §7's late-event measurement possible: a system that dropped these events would simply report a cleaner result.
  • State. Per-account keyed ValueState holds the rolling features; Spark's equivalent is GroupState with an explicit watermark check.
  • Checkpoints. EXACTLY_ONCE mode, 10-second interval, RETAIN_ON_CANCELLATION, and submit.sh restores from the newest retained checkpoint on restart.

Spark: the deliberate contrast

Spark Structured Streaming consumes the same Kafka topic with a 1000 ms trigger interval and applyInPandasWithState. It loads the identical model artifact, feature spec, ruleset and policy. The only difference between the two paths is the execution model itself — which is the point of CA2.

Result: the engines agree exactly, and differ enormously in latency

From parity run r_d48339d70bb9ceb4 on GCP (500 IEEE-CIS replay records, scenario replay, seed 20260917, 10 events/second, both engines):

Engine Rows persisted Distinct events Late Alerts e2e p50 e2e p95
Flink 1.20 500 500 0 69 92 ms 155 ms
Spark 3.5 500 500 0 69 3,862 ms 5,695 ms
Agreement metric Value
Events present in both engines 500
Same action 500
Different action 0
Max absolute score difference 0.000000000

Interpretation. The engines are in exact agreement — bit-identical scores on all 500 events — so the comparison genuinely isolates the engine. The ~42× latency difference is architectural, not a quality difference: Flink scores each record on arrival, while under a 1 s trigger a Spark event waits for the next batch boundary before it is even picked up. A p50 of 3,862 ms is close to what a 1 s trigger plus batch scheduling and scoring overhead predicts. Lowering Spark's trigger would narrow the gap; that variant was not run, so this report does not claim Spark is inherently 42× slower — it claims that at a 1 s trigger it is.

7. Experiment methodology, measurements, and interpretation

Full protocol: docs/benchmark-methodology.md. Raw evidence: docs/measured-results.md. Every run below executed on the deployed GCP stack (VM fraudwatch-pipeline, asia-south1-a) and every number was read back out of PostgreSQL or the Flink REST API.

Fairness controls. Both engines consume the same Kafka records from one generator run, with the same seed, the same model artifact, the same fs-1.1 feature spec and the same rules-1.1/policy-1.0 decision layer. Scores are compared row by row on event_id, so a coverage gap in either engine would appear as a non-zero only_flink/only_spark count rather than being averaged away.

7.1 Late-event handling — run r_b17d3ca811cf1137

Scenario late_events, 600 records at 5 events/second (~120 s), Flink only.

The 49 events flagged late are a 1:1 match with the 49 delivered more than 10 s after their event time. That is the expected result for a 5 s bounded-out-of-orderness plus a 60 s window with allowedLateness(ZERO): late events are marked, never silently dropped and never double-counted.

A negative result, reported. An earlier 150-event run at 10 eps produced late = 0. That was not a failure of the late path: its maximum delivery lag was 3,842 ms — inside the 5 s bound — and the run finished in ~15 s, before the 15–30 s delayed deliveries came due. The longer run above was designed specifically so the delayed path actually fires.

7.3 Lifecycle: wake and idle shutdown

Wake wake-39bed768b949, cold from sleeping: wake_requested → vm_running (+0.9 s) → services_up (+10.5 s) → ready (+13.6 s) — ~25 s total. An earlier failed wake, wake-362778af7f70, is preserved in the history with wake_failed followed by vm_stop_after_failure: the failure path stops the VM rather than leaving it running and billing, and the history is not rewritten to hide it.

Idle shutdown stop-0cdb13d13b32, measured at production settings (45-minute idle timeout, not a shortened test value): last activity 19:08:15 → idle_shutdown_started 19:53:43 = 45 min 28 s, then sleeping at 19:54:26 — VM stop took 42.2 s.

One unexplained detail is recorded rather than smoothed over: the drain call reported failed: ["r_5cf6b929471a5adc"] while the subsequent /internal/active-work check reported undrained_runs: 0, so shutdown proceeded. The events are consistent with a run that had already finished, but they do not prove it, and the drain failure is not explained by the recorded history.

7.4 What was deliberately not measured

Sustained throughput at saturation for either engine; p99 latency; latency under backpressure; CPU/memory cost per event; Spark at any trigger interval other than 1000 ms. The parity run was rate-limited to 10 events/second by the generator, so it measures latency at a low fixed arrival rate and is not a throughput benchmark. Saying otherwise would be the single easiest way to misrepresent this project.

Known defect at time of writing: CORS

Every API call from both deployed sites is currently blocked by CORS — 192 console errors across the two walkthrough recordings, all the same failure. The controller's ALLOWED_ORIGINS lists the project-number host form (fraudwatch-live-997216389793.asia-south1.run.app) while a browser loads the sites from the hash form (fraudwatch-live-2djxmgtj5a-el.a.run.app). Both host forms serve the sites; the origin check is an exact string match, so the hash form is rejected.

This is worth a moment in the viva because of how it was found. Section 6 of measured-results.md verified every route with curl and found 200 everywhere — and curl cannot see this defect at all, because the HTML and assets really are served correctly. It only appears once a browser performs the cross-origin check on the subsequent API calls. The fix is to add the hash-form origins to ALLOWED_ORIGINS on fraudwatch-control; it had not been applied at the time of writing because the deploying account's gcloud credentials had expired.

9. Testing, failure handling, reproducibility, security, cost

Testing. A Playwright (Chromium) end-to-end suite covers both apps; npm run typecheck passes across the monorepo. Browser capture scripts (scripts/capture_screenshots.mjs, scripts/capture_video.mjs) re-render both deployed sites on demand and fail loudly on any non-2xx route, so the evidence in this report is regenerable rather than hand-collected.

Failure handling. - Flink TaskManager loss → checkpoint restore, no loss, no duplicates (§7.2). - A failed wake stops the VM instead of leaving it running (§7.3). - While the VM is not ready the controller returns 503 {"error":{"code":"pipeline_starting_vm",…}} — an explicit unavailable state, never a fabricated empty result. - Invalid input is routed to dlq_events with a reason, not dropped. - Duplicate delivery does not create duplicate logical alerts (measured: 0 duplicates in §7.1).

Reproducibility. Fixed seeds (20260917), pinned versions, committed model artifact with its metadata.json and evaluation.json, versioned fs-1.1 / rules-1.1 / policy-1.0 contracts, and Docker Compose definitions for the full local stack. docs/local-setup.md, docs/apache-stack.md and docs/gcp-deployment.md document the paths from a clean machine.

Security. - No API key or secret appears in frontend code, Git history, logs, screenshots, this report, or any downloadable archive. Deployed secrets live in Secret Manager; local secrets live in an ignored .env. - Kafka, PostgreSQL, the Flink admin UI and the Spark admin UI are not exposed to the internet. - Operator actions require HMAC tokens (x-operator-token); service-to-service calls require x-internal-token. - Public visitors get bounded preset scenarios only — they cannot launch unbounded workloads or reach another visitor's private session. - The raw Kaggle dataset is excluded from the repository and from every shipped bundle.

Cost. See §8. Free Trial credit only; no paid upgrade; idle-stop and min-instances 0 as the controls.

10. Conclusion, limitations, future work, references

Conclusion

FraudWatch works end to end on real infrastructure. A real public dataset flows through real Kafka, real Flink and real Spark; a real LightGBM model scores every event and explains it; results persist to PostgreSQL and stream to two deployed websites that wake their own backend and put it back to sleep. The CA2 question has a measured answer: on identical input the two engines agree exactly — zero action disagreements, maximum score difference 0.000000000 — while differing by roughly 42× in p50 latency purely because of their execution models.

Limitations (current, honest)

  1. CORS defect on the deployed stack (§8) — the sites render, but their API calls are blocked. The fix is identified and one command wide; it was not applied before this draft.
  2. Model quality is modest — PR-AUC 0.1375 at 3.48% prevalence. Better than the baseline, not production-grade.
  3. No throughput benchmark — every latency figure is at a fixed 10 eps offered rate (§7.4).
  4. Spark measured at one trigger interval only (1000 ms).
  5. The §6 comparison predates the experiment runner — services/ops-agent/ is implemented and has completed a late_events experiment, but has not yet reproduced the parity run.
  6. R3_TEST_THEN_LARGE fires zero times and it has not been determined whether that is the data or the thresholds.
  7. One unexplained drain failure in the idle-shutdown history (§7.3).

Future work

Fix the CORS origins and recapture the screenshots with live data; re-run the parity comparison through the experiment runner so it is reproducible from the UI; sweep Spark's trigger interval to separate trigger cost from engine cost; run a genuine saturation/throughput benchmark; cost-sensitive threshold selection; drift monitoring on the streaming features.

11. Viva preparation — 20 questions and answers

1. Why is accuracy of 0.9059 not the headline? Because 96.5% of the test split is legitimate. Always predicting "not fraud" beats our accuracy. PR-AUC 0.1375 against a 3.48% base rate is the meaningful number.

2. What does PR-AUC 0.1375 actually mean here? A random classifier would score about 0.035 (the prevalence). We are roughly 4× that, and clearly above the logistic-regression baseline's 0.0961 — good, not production-grade.

3. Why LightGBM rather than a deep model? Tabular data with strong feature interactions, a small feature set, fast training, and TreeSHAP gives exact per-event attributions cheaply enough to run inline in a stream.

4. Where did the thresholds come from? Selected on the validation split (alert 0.10477, review 0.06955), then applied unchanged to the held-out test split, which was scored once. Choosing them on test would be leakage.

5. Are the model outputs probabilities? They are model scores. We report Brier 0.0321 and ECE 0.0055 for the test split, but we do not present the scores as calibrated probabilities elsewhere.

6. Why only 15 features? They must be computable from the stream. Any feature needing the full dataset or the future would inflate the offline score and then fail at runtime.

7. What is the difference between Flink and Spark here? Execution model only. Flink scores each record on arrival; Spark waits for a 1 s micro-batch boundary. Same model, same features, same rules, same policy.

8. Then why are the latencies 92 ms vs 3,862 ms? The 1 s trigger plus batch scheduling and scoring overhead. It is architectural, not a quality difference — and it is measured at a 1 s trigger, not an inherent property of Spark.

9. How do you know the comparison is fair? Both engines consumed the same Kafka records from one generator run, and we compare per event_id: 500 in both, 0 only-Flink, 0 only-Spark, max score difference 0.000000000.

10. What is event time and why use it? The time the transaction happened, not the time we received it. Processing time would make the result depend on network delay, so late events would silently change the answer.

11. What is a watermark? Flink's assertion that no event older than a bound will arrive. We use forBoundedOutOfOrderness(5 s) — 5 seconds of tolerated out-of-order arrival.

12. What happens to a genuinely late event? It goes to the late side output and is persisted with a late flag. We never drop it — dropping would make the results look cleaner than they are.

13. Prove the late path works. Run r_b17d3ca811cf1137: 600 events, 49 flagged late, and those 49 are a 1:1 match with the 49 delivered more than 10 s after their event time.

14. An earlier run showed late = 0. Was it broken? No. Its maximum delivery lag was 3,842 ms — inside the 5 s bound — and it finished in ~15 s, before the delayed deliveries came due. Nothing was late.

15. How do you survive a failure? EXACTLY_ONCE checkpoints every 10 s, retained on cancellation. We killed the TaskManager, the job restored from chk-80, restored = 4, with no event loss and no duplicate rows.

16. Why did the job still show RUNNING right after you killed it? The ~60 s heartbeat timeout had not elapsed. It is a detection delay, not survival.

17. How is this zero cost? Google Cloud Free Trial credit — not free hosting. Cloud Run at min-instances 0 and a 45-minute idle VM shutdown keep consumption near zero. No paid billing upgrade, no purchases.

18. What happens when someone visits while the VM is asleep? A validated visit triggers a wake (measured ~25 s). Until it is ready the controller returns an explicit 503 pipeline_starting_vm, never a fake empty result.

19. What is currently broken? CORS on the deployed stack: ALLOWED_ORIGINS holds the project-number host form while browsers use the hash form, so every deployed API call is blocked. The sites render; their data panels do not fill.

20. Why did your curl checks miss that? Because curl does not enforce the same-origin policy. The HTML and assets are served correctly, so every route returned 200. The defect only appears once a real browser performs the cross-origin check on the subsequent API calls — which is exactly why we re-verified both sites in Chromium.
